# Authentication and password controls

Signup requires separate, unchecked Terms and Conditions and Privacy Policy checkboxes, linked to /terms and /privacy. Email, Google OAuth, native Google and phone account-creation paths validate acceptance and store timestamps plus policy version 2026-10-14. Existing accounts are not silently marked as accepted and do not need to accept again to sign in. OAuth policy state is scoped to the verified OAuth flow and cleared with the other OAuth cookies. Login with a new Google identity without prior acceptance redirects to signup; existing identity login and email ownership-proof/linking behavior remain available.

Profile → Sign-in & account security → Password offers change-password with the current Circlo password, confirmation of the new password, and a fresh second factor when enabled. A recent session never substitutes for a correct current password. Account-scoped attempt limits, same-origin checks, normal password policy/cost and conditional row-locking updates apply. Changes revoke existing sessions, pending sign-in challenges and reset links; the user signs in again. Device encryption keys and Google identity links are not replaced.

Google users who never set a Circlo password use the profile email setup link. They must not enter their Google password into Circlo. The email recovery flow establishes a Circlo password while retaining Google and MFA. Phone-only placeholder addresses are not offered a nonfunctional email reset option.

Forgot password remains linked from login and is also available in profile. Requests have independent IP/address limits, a serialized one-minute send cooldown, hashed high-entropy single-use links, one-hour expiry, canonical URLs, escaped email templates and bounded Resend calls. Failed provider sends invalidate the token while retaining the cooldown. Public responses acknowledge a request without claiming delivery or revealing account existence. Successful email recovery verifies ownership, revokes old sessions/challenges and preserves MFA. Concurrent reset consumption has exactly one winner and rechecks expiry after locking.

Tests use disposable loopback databases and mocked provider transport. Coverage includes both checkbox requirements and persisted acceptance, mobile profile controls, wrong current password with unchanged hash, email setup action, successful password change/sign-out/new login, CSRF, MFA enforcement and recovery code use, expired/replayed/concurrent reset links, cooldown and rejected provider delivery. Real delivery checks must use an explicitly designated mailbox; provider acceptance does not prove inbox placement or that the recipient read the message.
