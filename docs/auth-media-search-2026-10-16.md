# Authentication, media and public search review

This change preserves mandatory email verification, MFA where enabled, device approval, same-origin checks, rate limits, session revocation and cost-12 bcrypt. No new service or paid plan is introduced.

## Authentication

- Registration already rejects duplicate usernames through a case-insensitive lookup and unique database index. That constraint remains the final authority during concurrent registrations. Duplicate responses now include three bounded, database-checked suggestions. Suggestions are not reservations; submission checks again. No public availability endpoint was added.
- Login identifiers, password confirmation, recovery email addresses and reset tokens now have explicit size bounds. Email whitespace is normalized consistently. Passwords are never trimmed, and the existing 72-byte bcrypt boundary remains enforced.
- Email-verification and resend fields use the same bounded email schema as signup/recovery.
- Password changes already reject incorrect current passwords before updating the hash or revoking any session. Client-side validation now catches weak/mismatched new passwords sooner. The existing reset-email action and recovery link stay visible. Google-only users set a Circlo password using email recovery, never their Google password.
- Existing authorization regressions cover Google nonce/audience/state binding, replay, account switching, consent, CSRF, MFA, wrong passwords, reset expiry/single use and session revocation. These tests do not establish that all possible vulnerabilities have been eliminated.

## Media

- 10 MiB maximum plaintext per file and per attachment batch. Multiple files share that batch budget; send larger batches separately. Up to five files remain supported.
- AES-GCM adds 28 bytes per file. The private storage bucket permits 10 MiB + 28 bytes; its `public` flag remains false. Application media reads still enforce account/conversation authorization.
- HTTP multipart reads are capped at 11 MiB including metadata; Next Proxy buffers at most 12 MiB, avoiding its former 10 MiB truncation before the application reader.
- Profile/group/status photo inputs accept up to 10 MiB. Isolated photo reconstruction retains its 12-megapixel, time/concurrency limits and 3 MiB encoded-output ceiling, keeping displayed photos small. Existing scanner requirements for readable raw media are retained; raw video status is not silently enabled on the scanner-free starter deployment.
- Production Supabase bucket was previously capped at 3 MiB, independently of source-code settings. The bucket limit was updated through the server SDK without exposing credentials. Before-state is recorded only in ignored local release evidence. Render had no MAX_IMAGE_MB/MAX_FILE_MB/MAX_AVATAR_MB override, so the new defaults apply without changing secrets.

## Public pages and indexing

Public sitemap entries: `/`, `/privacy`, `/terms`, `/whatsapp-alternative`.

Source files: `src/app/sitemap.ts`, `src/app/robots.ts`, `src/lib/public-metadata.ts` and each public page. Next generates `/sitemap.xml` and `/robots.txt`; there are no manually maintained XML/text duplicates.

Each public page has its own title, description, canonical URL, Open Graph and Twitter card. The social preview image is first-party and generated by `scripts/generate-social-card.mjs`.

Authentication, account, invitation and API routes send `X-Robots-Tag: noindex, nofollow`. Login/signup/forgot-password can be crawled so crawlers can read that directive. Private app/API/token-bearing paths remain disallowed in robots and protected by real authentication; robots is not an access-control mechanism. The PWA offline page is noindex.

The duplicate `/register` alias permanently redirects to `/signup`. The historical standalone landing prototype has moved out of public into a test fixture; `/circlo-landing.html` permanently redirects to `/`. Preview tests retain the fixture, and production browser tests cover the actual Next pages.

The WhatsApp alternative page uses original, factual content. It explicitly acknowledges WhatsApp's default personal-message/call encryption, discloses Circlo metadata/recovery limitations and has no affiliation claim. Ranking above WhatsApp or obtaining Google indexing is not guaranteed by technical SEO.

## Google Search Console setup

1. Add a **Domain property** named `circlo.chat` (no `https://` or path).
2. Add the exact DNS TXT verification value Google provides at your DNS provider, then verify ownership. Keep the record. No tracking script or Google login credentials need to be added to Circlo.
3. Submit `https://circlo.chat/sitemap.xml` in the Sitemaps section (or `sitemap.xml` if Google presents a URL-prefix input).
4. Use URL Inspection → Test live URL → Request indexing for the homepage and `/whatsapp-alternative`. Google decides whether/when to index.
5. Review Page indexing, Core Web Vitals, HTTPS and Security issues. Private/authentication URLs intentionally excluded are expected; do not request indexing for chats or token URLs.
6. `robots.txt` is discovered automatically. Do not submit it as a sitemap. Do not submit the old Render/Vercel domains as the canonical site.

Sources: [Google ownership verification](https://support.google.com/webmasters/answer/9008080), [Google sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap), [Google noindex guidance](https://developers.google.com/search/docs/crawling-indexing/block-indexing), [WhatsApp security explanation](https://faq.whatsapp.com/990878486361178/).

## Verification scope

Local tests use disposable loopback PostgreSQL and fake accounts. Google/mail provider integrations are mocked; no external paid calls. Public-page crawling follows internal links and fragments only, checks real 404s/redirects, canonical/description/noindex headers, sitemap/robots and 320/390/1280 layouts. It never submits production authentication or account-recovery forms.

Supabase advisors additionally flag unused Supabase Auth options and a deny-by-default `public.profiles` table with RLS but no policy. Circlo's authentication/database use its own server/Neon implementation; enabling unrelated Supabase Auth options would not protect that custom login. No broad policies were added to silence an advisor. The pre-existing reviewed development-only dependency exception remains separately tracked by the dependency audit.
