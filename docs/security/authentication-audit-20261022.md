# Circlo authentication audit

Baseline: `75398ff4bfac249f59607d26156393eb4d6cd685` (merged security and mobile UX changes). Scope: application authentication, session/recovery transitions, trusted devices and authorization boundaries. No live exploitation, production database writes, credential rotation, merge or deployment was performed.

The [130-case matrix](authentication-attack-matrix-20261022.md) and [machine-readable catalogue](authentication-attack-matrix-20261022.json) distinguish existing controls, source inspection, new regressions and deployment-dependent checks. **130 cases does not mean 130 vulnerabilities or 130 independently executed penetration tests.**

## Confirmed weaknesses and fixes

| ID | Severity | Condition and impact | Fix / regression |
|---|---|---|---|
| F1 | High | A password or factor proof can be verified, then account credentials/revocation can change before a new session or MFA challenge is persisted. The old proof is not consistently compared with the new account state. Existing device approval limits the resulting session, but stale proof must not mint credentials. | Compare the verified password-hash/revocation snapshot under the account lock at issuance; recheck suspension and MFA enrollment. Test both an already-stale snapshot and issuance blocked behind an actual reset/account row lock. Recheck completed-factor snapshots before issuing cookies. |
| F2 | High | MFA management authorizes before its writes. A delayed setup can overwrite a just-enabled secret, or a pre-enrollment/revoked actor can reach factor changes using an earlier authorization result. | All setup, enrollment, disable and recovery replacement operations lock/revalidate the account, live actor session and factor. Account ownership, approval and MFA epoch are checked inside the transaction. User/session locks use a consistent order. MFA challenges from an earlier factor epoch are rejected. |
| F3 | High | Enabling MFA invalidates old sessions through the enabled-at comparison, but deleting the factor removes that comparison. Previously blocked cookies can become usable again if their persisted sessions were never revoked. | Disabling MFA atomically advances the revocation watermark, revokes sessions and deletes pending challenges before deleting the factor. Clear cookies and require sign-in again. Regressions check original access cookies, the modifying session and refresh credentials. |
| F4 | Medium | Fresh native Google and completed Firebase phone ID-token proofs can be exchanged repeatedly during the accepted freshness window. A captured bearer token can mint more than one Circlo session. | Atomically consume a digest in the shared store after provider validation; never store raw provider tokens. Keep phone profile-completion retries possible before consuming the completed proof. Google native exchange is tested with an isolated signing key/local JWKS; phone single-use concurrency is tested through the same primitive. New Android requests use a fresh nonce to avoid identical cached credentials on separate attempts. |
| F5 | Medium | A signed mobile Google handoff issued before an account revocation can be exchanged afterward because exchange loads the newer user record without comparing ticket issuance to the cutoff. | Bind a millisecond issuance claim to the ticket and reject pre-cutoff handoffs. Retain PKCE, policy agreement and shared single-use redemption. |
| F6 | Medium | Logout clears access/refresh credentials but leaves an unfinished MFA challenge valid. | Delete the presented pending challenge by digest and expire its HttpOnly cookie. An HTTP regression attempts completion after cancellation. This covers unconsumed challenges; it does not claim that logout can cancel every concurrently completing independent login. |
| D1 | Defense in depth | Some internally signed JWT readers rely on implicit/optional claim handling and accept a broader profile than the issuer creates. This is not proof that an attacker can forge signatures. | Explicit algorithms and required expiry/issuance claims, bounded lifetimes, session UUID/timestamp validation and token-type checks where applicable. Unit tests cover alternate algorithms, absent/overlong expiry, cross-purpose audiences and malformed identities/times. |

## Verification

- `npx tsx --test tests/authentication-token-validation.test.ts tests/mobile-policy.test.ts`: targeted token/snapshot unit regressions.
- `npx tsx scripts/test-authentication-audit.ts`: disposable database only; checks stale/in-flight credential changes, actor/MFA epoch checks, session/refresh revival, completed-factor revocation, native Google replay and mobile cutoff. Requires `LOAD_TEST_ADMIN_URL` pointing to `127.0.0.1/postgres`; creates and removes only its randomly named audit database.
- Existing account-security HTTP tests now check unfinished-MFA logout cancellation and access rejection after factor removal.
- Quality CI runs the new database audit as part of the session/security regressions. Existing production browser/device workflows, account authorization, credential-canary checks, role isolation and Android compilation remain enabled.
- Local type checking and targeted token tests passed during implementation. Full CI results must be checked on the PR's latest commit; do not infer completion from this static document.

The local Windows image-worker unit failures observed in the earlier task are unrelated to these authentication changes; Linux CI is the supported full image-processing verification environment.

## Operational changes

Disabling MFA now signs out all devices, including the requesting browser. Enabling MFA retains the existing protected device-enrollment flow. Password hashing and remote identity verification stay outside the short credential-issuance transaction; the transaction adds database checks to protect security-sensitive state transitions rather than holding locks during bcrypt/provider work.

Native provider proofs become single-use. A rejected/lost exchange requires fresh provider verification. Rebuild the Android APK to receive the new per-request Credential Manager nonce; the server-side single-use control also applies to older clients. In-flight mobile handoffs created before this release, without the new issuance claim, must restart sign-in (their previous lifetime was only two minutes). No encryption identity, chat key, schema migration or new production secret is introduced.

## Residual risks and live evidence still needed

- **R1: email-membership disclosure.** Signup intentionally reports an already registered email. This is an enumeration/privacy tradeoff, not a demonstrated password/MFA/device-approval bypass. Changing it requires consistent registration/delivery UX, not merely changing one error string.
- **R2: reset timing.** Forgot-password uses generic response bodies, but only an existing account awaits email delivery. The timing difference is visible in source; no live statistical enumeration claim is made. Durable queued delivery is the preferred separate remedy so response timing does not depend on provider delivery and recovery mail is not lost on a process restart.
- **R3: TOTP seed key separation.** TOTP seeds are server-readable database fields. A database read compromise would expose them; provider disk encryption does not replace application-level key separation. A dedicated key-management/rotation/migration design is required before claiming this additional protection. Recovery codes and reset/refresh tokens are already stored as hashes.
- Confirm the live runtime database role/RLS, CSP enforcement, proxy trust, TLS, Google/Firebase console configuration, mail-provider security, signing-key management and suspicious-authentication alerts. These cannot be certified from repository code or mock providers. Firebase phone sign-in is paused in Starter Mode; a live/provider-integrated phone verification was not performed.
- Real Android sign-in and deployment configuration require a physical-device check after the owner merges/deploys. Synthetic test success does not certify protection against phishing, a compromised user device, stolen unused bearer proofs or an already compromised application server.
