# Circlo security audit — 22 October 2026

## Executive assessment

Scope: repository `mudassirishfaq94/maddychats`, starting at main `4dd0490f3238dba032e8fac1e433852034dbf895`, and disposable CI databases. No production probing, real-user data access, infrastructure changes, secret rotation, destructive migration, or storage migration was performed.

A **High** object-authorization flaw was reproduced: an authenticated outsider could call DELETE `/api/messages/{known-id}/star` and receive another conversation's message DTO. UUID unpredictability does not authorize access. Legacy readable content, sender/conversation metadata and attachment descriptors could leak; E2EE ciphertext does not by itself grant decryption. The fix authorizes the shared single-message reader as well as the HTTP action.

The same review identified inconsistent enforcement of per-user history visibility across bookmarks, pins, media/files/links, replies, notifications and retained realtime events. A shared, parameterized SQL predicate now enforces current membership, non-deleted conversation, the clear watermark, and per-user deletions. Persisted message events are rehydrated before delivery. One Low proxy-configuration inconsistency was also corrected.

**Overall assessment:** the original code had a confirmed High issue. Proposed code fixes require the PR's final green regression checks and deployment before protecting production. Live bucket privacy, actual database privileges, edge TLS/header settings and provider restrictions remain unverified. Passing tests is not proof of absence of other vulnerabilities.

## Architecture inspected

- Next.js 16.4.1 App Router, React 19.2.6, Node 22 target; Android loads the hosted application. Pinned Next.js data-security and Route Handler guides were read.
- Custom HS256 access JWTs, HttpOnly Lax cookies, rotating persisted device sessions, account revocation timestamps, MFA and device-approval gates: `src/server/{jwt,session,device-sessions,authentication}.ts`. Supabase Auth is not the application's authentication boundary.
- Drizzle plus parameterized `pg` against PostgreSQL. A private runtime role can access application rows; API routes enforce per-user ownership. RLS/privilege revocations isolate browser Data API roles; this is not per-user database RLS.
- Supabase Storage service-role adapter or private local storage, authenticated media routes, encrypted attachments, bounded staged uploads, reconstructed readable photos and optional/required-by-mode scanner paths: `src/server/{storage,upload-safety,status-photo,staged-media}.ts`.
- SSE backed by PostgreSQL events/LISTEN, private FCM/Web Push, temporary-room credential cookies, external Google/Firebase authentication proofs. Render and Docker configuration inspected as repository references, not assertions about deployed state.
- AST-assisted inventory: [127 API modules / 176 explicitly exported handlers](route-inventory-2026-10-22.md). Authentication markers are module-level evidence; exhaustive dynamic testing of every branch is not claimed.

## Confirmed findings and reproduction

### SEC-01 — High: cross-conversation message disclosure through unstar

Before: `src/app/api/messages/[id]/star/route.ts:DELETE` deleted only the caller's own star but then called `src/server/chat.ts:getMessageDTO`, whose lookup required only `messages.id`. The latter loaded text/ciphertext and hydrated metadata without membership.

Reproduction uses only disposable Alice/Bob/outsider fixtures and a known fixture message ID. `DELETE /api/messages/{id}/star` as outsider must return 404 with no `message` field. In regression-only commit `8e8ba5fffed81ab13a07118ac0162f89af6299ef`, Quality job `119586067674` failed `Unstar must not read a message from another conversation` (actual 200); reliability job `119586067270` returned a full DTO to the outsider where null was required. This establishes a real path, not a UUID-brute-force claim.

Fix: authorization in `getMessageDTO` before hydration, explicit origin/object check in unstar, and negative HTTP/SQL tests with authorized controls. No decryption or key protocol is changed.

### SEC-02 — Medium: secondary paths ignored per-user history revocation

Affected functions: `listStarredMessages`, `listPinnedMessages`, `listConversationMedia`, `listConversationFiles`, `listConversationLinks`, reply-parent hydration/creation in `src/server/chat.ts`; `GET /api/media/[...path]`; notification delivery; media reply targets. Membership-only attachment access ignored `clearedAt`; starred reads did not recheck current membership. Pinned/reply data could restore individually hidden content.

Fix: shared SQL predicate `src/server/message-visibility.ts:messageVisibleTo`, applied before content selection/hydration. It excludes messages at or before the database clear timestamp, missing membership, deleted conversations and per-user deletions. Global deletion/expiry tombstones retain their separate existing redaction rules. Delete-for-me returns an identifier-only acknowledgement compatible with the client's row-removal flow, rather than loading content after hiding it.

Regression coverage checks an exact PostgreSQL timestamp boundary (without JavaScript millisecond truncation), valid member controls, inaccessible old file URLs/notifications, hidden pins/bookmarks/galleries/links, reply parents, and removed-member bookmarks. These tests prove server visibility; clearing does not erase copies already downloaded by a participant or their encryption keys.

### SEC-03 — Medium: persisted realtime payloads outlived read permission

`src/app/api/realtime/stream/route.ts:deliver` previously emitted a retained message payload after account authentication without reloading message visibility. Clear, per-user deletion or conversation removal could occur after event persistence; subsequent edit/global deletion/expiry could also make the serialized payload stale.

Fix: `src/server/realtime-visibility.ts:currentMessageEvent` rehydrates new/update/delete message content using current per-viewer authorization before emission. A serial queue preserves message order and caps outstanding message authorization at 100; slow consumers reconnect rather than accumulating unbounded pending work. Failure closes the stream instead of emitting unverified content. Existing session eligibility checks remain.

Regressions retain an old DTO, then clear history/remove membership and assert replay eligibility is null. A production HTTP regression also seeds 201 owned message events and consumes all their SSE IDs, crossing the 200-row replay-page boundary. Replay drains authorization work in batches of 50 so its pages cannot overflow the live queue cap. Existing production browser reliability flows validate real SSE delivery and reconnection. This adds server read work per content event; production throughput should be measured before scaling up rather than removing authorization for speed.

### SEC-04 — Low: inconsistent temporary-room proxy configuration

The three temporary-room routes used `TRUSTED_PROXY_HOPS` and `Boolean(RENDER)`, while the shared application resolver uses `CLIENT_IP_TRUSTED_HOPS` and exact `RENDER === 'true'`. Explicit non-Render trusted-hop deployments could collapse unrelated users into the unknown-IP quota; a literal `RENDER=false` was interpreted as true. This is an availability/configuration defect, not a demonstrated Render IP-spoofing bypass.

Fix: all three call the existing `src/server/http.ts:clientIp`, preserving its tested edge trust/fail-closed policy. Existing IP resolver tests and temporary-room browser/API regressions cover the shared policy and functionality.

## Remaining risks and owner verification

1. Confirm Supabase bucket privacy, Storage policies, service-role confidentiality, actual production runtime DB role, RLS/grants/migration enrollment, effective TLS/CSP/CORS/headers, privileged MFA and provider API key restrictions. Repository intent is not deployment evidence.
2. Private runtime RLS intentionally allows all backend rows. Migrating to per-user database RLS is a broad architecture change requiring explicit design/approval, not an automatic policy edit.
3. Consider adaptive public-form anti-bot protection and a bounded denied-admin-action audit policy. Their absence is recorded, not silently solved with unavailable provider credentials or unbounded logs.
4. Keep the braces exception visible and time-limited; encrypted uploads cannot be plaintext-inspected server-side. Continue device/throughput testing, especially realtime authorization under load.
5. Planned media-storage migration (Cloudflare R2 or another evaluated provider) must preserve private buckets, authenticated reads, encrypted bytes, retention/deletion, existing links and rollback. It is a separate roadmap item and was not performed by this audit. Render keep-alive/paid hosting is also separate.
