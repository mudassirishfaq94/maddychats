# Security audit — 2026-10-13

Scope: the existing Next.js application, 106 API entrypoints, server authorization helpers, environment handling, public files, all reachable Git history, npm dependencies, Neon runtime permissions and linked Supabase Storage. This is a code/configuration audit with regression tests, not a guarantee against every attack or an independent penetration test.

## Fixes

| Finding | Change |
|---|---|
| Origin guard compared only hostnames and trusted the request Host | Compare full origins against server configuration. Support the configured custom domain and Render-provided service alias. Reject altered protocols, external hosts, credentials in URLs and cross-site Fetch Metadata. |
| HTTPS cookie detection could accept a caller's downgrade headers | Configured production HTTPS takes priority; local HTTP tests still work. |
| Admin shell authorization ran only in the browser | Server layout requires a fresh database-backed administrator/moderator check before rendering the shell. Every admin API keeps its independent role checks; mutations retain MFA, recent authentication and transaction-time actor locks. |
| Private media could be cached for an hour | Private media uses `private, no-store`; private API responses receive the same default in Proxy. Version/auth capability metadata retains separate public behavior. Static media assets never rotate refresh tokens. |
| Native notification taps accepted arbitrary navigation URLs | Allow only first-party `/app` paths or validated UUID chat deep links. Reject executable, external and malformed destinations. |
| Media/push logs and raw database/provider exceptions exposed unnecessary details | Remove token/title/storage-path debug logging; server errors retain only a safe error category and SQLSTATE, without raw messages, SQL, parameters or provider headers. |
| Password forms counted characters instead of bcrypt's 72 UTF-8 bytes | Enforce byte length for registration, resets and admin password changes; hashing also rejects truncation. Existing hashes and cost 12 are preserved. |
| Unknown-account login skipped password work | Compare a dummy cost-12 hash through the same bounded worker pool, reducing the username timing distinction. Existing IP rate limits and queue bounds remain. |
| User filenames interpolated into download headers | Encode Unicode filenames using `filename*` and a bounded ASCII fallback, preventing CR/LF and delimiter injection. |
| Runtime database connection used an owner role with database/role creation and RLS bypass | Prepare a separate runtime role with table DML, sequence access and read-only migration metadata. Existing RLS stays enabled; explicit policies authorize only this private backend role to perform the server's existing operations. Other roles remain denied; per-user access is enforced in the application. Migration tooling uses `MIGRATION_DATABASE_URL`; startup synchronizes new-table grants/policies and removes owner credentials from the web child's environment. Runtime role cannot create tables/roles/databases, truncate tables or become the owner. |
| Clearing a draft could leave its old encrypted record until a throttled browser's debounce fired | Trigger encrypted-store deletion immediately on clearing input. The mobile regression now observes transaction completion before testing reload, instead of using a fixed 800 ms delay. |
| Unused Supabase profile tables retained public API grants | Revoke all privileges from `anon` and `authenticated` while keeping RLS, rows and service-role Storage access. The app uses Neon account tables, not these legacy tables. SQL verification confirms SELECT/TRUNCATE are denied. |

## Existing controls reviewed

- Production JWT configuration fails closed without a sufficiently long key; HttpOnly, Secure production cookies use SameSite=Lax. Refresh tokens are hashed, rotated and device revocation is checked against the database.
- Password resets and MFA/recovery challenges expire and are consumed once. Administrative writes require MFA and recent authentication. Role decisions come from the database, not user-editable metadata.
- Conversation, media, group, community, status, device-key and account-data operations enforce server-side membership/ownership/privacy checks. The API inventory records direct entrypoint guards; deeper helper guards and token-authenticated public endpoints were reviewed separately.
- Inputs use bounded streamed JSON/multipart reads and server validation. Text is rendered with React escaping; no application `dangerouslySetInnerHTML`, `eval` or `new Function` sinks were found. Encrypted message text is never destructively HTML-sanitized.
- Database queries use Drizzle/parameterized PostgreSQL parameters. Shared rate limiting is atomic and fails closed when its store is unavailable. Uploads keep MIME/size/pixel limits, photo reconstruction and required configured scanner checks.
- CSP enforcement is enabled live. Existing HSTS, nosniff, framing, referrer and permissions headers remain. Production debug/profiling flags are disabled; `.env`, `.git/config` and package metadata probes returned 404, and anonymous admin/chat APIs returned 401.
- Both Neon client connections were inspected at their TLS sockets: encrypted transport and certificate authorization were true. `pg_stat_ssl` can describe an internal provider hop and is not proof of the external client transport. Prepared runtime URLs explicitly use `sslmode=verify-full`.
- Supabase buckets are private; the app bucket limit is 3 MB. No public Storage read policies exist. Service-role credentials stay in the server adapter.

## Secrets and dependencies

Gitleaks 8.30.1, downloaded from its official release and checksum-verified, scanned 298 commits. Six exact historical findings were reviewed: four disposable loopback integration credentials, one Cargo lockfile checksum and one Firebase public client configuration key. `.gitleaksignore` contains only those exact historical fingerprints; future findings remain blocking. CI now scans full reachable history with redacted output. A separate comparison of current live private configuration against 1,734 historical text blobs found no matching server secret. Secret values were not included in reports.

Compatible patch updates: Supabase JS 2.117.3, Drizzle ORM 0.45.4, Drizzle Kit 0.31.11, jose 6.2.12, pg/types 8.23.1, PostCSS 8.5.30 and tsx 4.23.15. Runtime npm audit reported zero advisories before changes; rerun dependency checks after updates and in CI. Avoid unrelated framework/native major upgrades as a security workaround.

There remains an existing development-only `braces` advisory and dependent ESLint glob packages. Its exact-version, expiring exception remains visible in `dependency-audit-exceptions.json`; it must not be described as zero total dependency findings. No production dependency uses that exception.

## Verification and operational limits

New tests cover forged origins, the Render alias, HTTPS cookies, notification URL attacks, international/hostile filenames, password byte boundaries, dummy bcrypt work, safe logging and startup credential separation/failure. The HTTP authorization suite also runs with the limited database role, rejects CREATE TABLE/TRUNCATE and checks ordinary users cannot receive the admin shell or admin data. Existing integration, MFA/reset/session, encrypted device, upload and mobile browser suites remain required by CI before deployment.

The Firebase client key is intentionally public configuration, not a server authentication credential. Its Google Cloud API restrictions and administrator account recovery/2FA settings require access to the relevant provider console; this audit does not assert those external account controls were verified. Supabase Auth advisor settings do not govern this app's custom Neon-backed authentication. The remaining provider account and development advisory limitations should be reported explicitly.

## Deployment and rollback

1. Run quality/security tests and the full-history scan before publishing/deploying.
2. Apply `docs/database/runtime-role.sql` with the migration owner, enroll a random runtime password privately and verify the restricted connection. Keep credentials outside Git.
3. Configure owner `MIGRATION_DATABASE_URL` and runtime `DATABASE_URL`/direct `REALTIME_DATABASE_URL`. Keep canonical `CLIENT_URL`; the host's `RENDER_EXTERNAL_URL` is the explicit first-party alias.
4. Deploy the verified commit and check both first-party origins, authenticated readiness, fake-account authorization, encryption/media and cleanup.
5. Roll back the code and database URL environment values together if necessary. Keep the limited role until it is no longer used; remove its grants/role using the migration owner only after reverting the connections. The Supabase grant migration changes no rows; restore old grants only if an independently verified legacy client requires them.
